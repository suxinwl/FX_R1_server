# R1XiaoZhi_MediaServer

> **版本 v1.2.3（2026-11-07）** —— 远程排障先看顶栏版本号（或 `/api/health` 的 `ver` 字段）。
> - ① **修「容器偶发意外停止」**：`/s/<i>` 与 `/r/<src>/<rid>` 的音频转发原来用
>   `AbortSignal.timeout(20s)` 管**整条连接**。播放器一暂停/拖进度就背压 → 上游 body 没人消费
>   → 20s 后 abort → `Readable.fromWeb(up.body)` 的 error 无人接 → Node 直接退出进程。
>   compose 里是 `restart: unless-stopped`，几秒后又起来，表现就是「偶发停止」。
>   现在拆成「等响应头 20s」+「传输期 60s 空闲看门狗」（`src.isPaused()` 为真不算上游死），
>   `src`/`res` 全挂 error，真掐断用 `destroy()` 而不是 `end()`（后者会让 Content-Length
>   短半截，被播放器当正常 EOF）。回归脚本在 `_tests/`。
> - ② 书列表 `cover` 改 NAS 绝对地址（v1.2.2）—— 相对路径会打到设备 8080，封面全 404。
> - ③ v1.1.0 及更早的变更见文末「版本记录」。

一个容器、一个端口（**8100**）解决 R1 小智的全部音源需求：

| 内容 | 来源 | 合并前 |
|---|---|---|
| 本地音乐库 | 扫 NAS 音乐目录（内嵌标签用 music-metadata 读） | r1-music 8010（Python + mutagen） |

（R1 的「音乐源」里只写这一行，8010 那行删掉）

## 1. 把目录放到 NAS

假设放到 `/volume1/docker/R1XiaoZhi_MediaServer`（用 File Station 拖进去即可）。

## 2. 把原来的电台清单搬过来（有电台才需要）

```bash
# 先找到老 r1-music 容器里 radios.json 在哪
docker exec r1-music sh -c 'find / -name radios.json 2>/dev/null'
# 假设输出 /app/radios.json，拷进新容器的 files/ 卷
docker cp r1-music:/app/radios.json /volume1/docker/R1XiaoZhi_MediaServer/files/radios.json
```

格式是 `[{"name":"Hit FM","url":"http://..."}]`（也认 `stream/addr/src` 这几个别名）。

## 3. 改 docker-compose.yml 里的音乐目录

```yaml
- /volume1/music:/music      # 冒号左边改成 NAS 上你自己的音乐目录
```

## 4. 起容器

先**停掉旧的两个容器**（它们占着 8100 / 8010）：

```bash
docker stop r1-music mini-lx && docker rm r1-music mini-lx
```

再用 Container Manager 的「项目 → 新增 → 选 docker-compose.yml」，或命令行：

```bash
cd /volume1/docker/R1XiaoZhi_MediaServer
docker compose up -d --build
```

### 搜索也是走落雪的（2026-10-18 起）

`/api/search` **先问落雪**（`GET {lx}/api/music/search?source=&name=&limit=`），
一个都没搜到才回落脚本音源。好处是**搜索与取链同源** —— 列表里的 rid 是落雪自己发的，
它取链一定认得；顺带每条结果都带 `_types`（这首有哪些音质档），起播前就知道该问哪一档。

| | 以前（脚本音源搜索） | 现在（落雪搜索） |
|---|---|---|
| mg | 列表里有，点了 500「咪咕找不到」 | **直接出真链**（实测 367ms） |
| kg | 缺 hash，unknow error | 落雪侧 kg 源本身没配 ⇒ 走跨源顶替（kw 同名歌，1342ms 出声） |
| kw / wy / tx | 能播 | 能播 |
| 速度 | 348ms（命中缓存 24ms） | 420ms（五源并发，未缓存） |

★ 关键机制：搜索时把落雪返回的**整条 songInfo**（含 `_types`）暂存在内存里，
起播那一刻按 `source:rid` 查回来**原样回传**给取链接口 —— 少了这份信息 mg 一律 500。
入池的歌会把 `_types` 一起落进 `files/pool.json`，容器重建也还在。

> 为什么出厂是 128k：绝大多数歌本来只有 128k；而落雪的高音质档命中的常是
> 中转地址（`music-dl.sayqz.com/...`，拿得到链但出不去），实测要先白等 2 秒才退到
> 128k 拿到酷我真链。直接从 128k 起手 = 少一次失败 + 快 2 秒。

### 网络电台可以自己加 / 删

电台块底部一行：**电台名 + 流地址 + 添加**；每行右侧 `✕` 删掉。

- 删改是**整体覆盖**，所以一次加/删一个台也是把整份清单发回去；
- 加完不用重启，但**小智那边要 `op=reload`** 才会看到新台。
- ★ **默认** R1 拿到的就是你填的那个**原始流地址**（设备直连源站）。
  只有显式设 `RADIO_PROXY=1` 才会改写成 `/radio/<base64url>` 走本机代理
  （见下一节：2026-10-18 的对照实验结论是「直连更好」）。 `/api/radios`
  无论哪种情况都吐原始地址，这样你在 Web 上改清单不会被套娃。

### 网络电台为什么会「播几秒停一会儿 / 同一句话反复播」（2026-10-18 修）

电台条目里是**公网直播流**（chunked、无 Content-Length、24 小时不断）。
实测 `http://lhttp.qtfm.cn/live/339/64k.mp3`：

| 项目 | 实测值 |
|---|---|
| 真实码率（mp3 帧头逐帧解析） | **恒定 64 kbps = 8.00 KB/s** |
| 直连源稳定供给 | **12.8 KB/s**（见下：这点很重要，最后一版错的根） |
| 刚连上头 2 秒 | ~40 KB/s 猛推 ⇒ 所以「一点就出声」 |

排查过程中出现过**两种症状**，分别对应**两个不同的坑**，都修完了：

| 症状 | 真凶 |
|---|---|
| 播 6 秒 → 停 3 秒，精确循环，每个台都一样 | 代理把写背压传导回上游（`up.pause()`）⇒ 电台判定慢客户端掐断 ⇒ 重连 + 重新预填充 |
| 播的内容**反复重复**（同一句话循环），不停顿 | `res.write()` 返回 false 就没清缓冲 ⇒ **同一份数据被反复写出**（真正的大坑，见下） |
| 上面两条修完后**又**回到 6 秒 / 3 秒 | 跟代理无关：源只有 **1.0x 实时**供给 ⇒ 设备**零余量**（下面整节都在讲这个） |

#### ★ 最关键的坑：Node 的 `res.write()` 从不拒绝数据

这是本模块最难查的一行。Node 的 `res.write()` **一定会把数据塞进输出队列**，
返回 `false` **只**表示「内部缓冲超过 highWaterMark（默认 16KB），建议先歇会儿」。
我们一次要吐 64KB ⇒ **必然**返回 false。于是：

```js
if (!this.safeWrite(out)) break;   // ✗ 每次都在这儿退出
this.buf = [];                     //   永远走不到 → 水库永不扣账
```

下一次 `drain` 又把同一份 64KB（≈8 秒内容）再写一遍 ⇒ 设备就是在同一段话里循环。
实测这条路能让客户端 **12 秒收到 12.5 GB**。正确做法是无条件扣账，
只按返回值决定要不要等 `drain`（已写在 `Sub.pump()` 的注释里）。

#### 现在的做法

**① 上游连接池（每个电台 URL 一条持久连接，长期不断）**

设备侧的取流器是 Android 5.1 的 `NuCachedSource2`，日志里能看到
`Cache full, done prefetching for now` —— 它的策略就是
预取 → 缓存满 → 停止读 → 消耗 → 见底 → 再预取，**并会周期性断开重连**（固件行为，改不了）。

电台 CDN 对每个**新连接**都会先吐一段开场缓冲（约 6 秒的台标/垫乐），
同一时刻所有新连接拿到的都是同一段 ⇒ 设备每重连一次就再听一遍开场。

所以：**客户端爱重连就重连，到源那条连接始终只有一条** —— 从根上没有第二次「开场」。

**② 每个客户端一个水库，背压互不影响，也绝不回头掐上游**

**③ 客户端没走，就绝不 `res.end()`**
一旦 end，设备会判定「这首播完了」，而播放列表里只有电台一条 ⇒ 立刻从头重播
⇒ 又一次新连接 ⇒ 又一次开场。`RADIO_RETRY` 因此给到近乎无限。

**只对设备生效，R1 侧零配置** —— 设了 `RADIO_PROXY=1` 之后，`/index.json` 里电台的 URL
会自动指向本机代理（默认不改写，见下面「5 号证」）。

### ★ 4 号证：6 秒 / 3 秒的真凶是「零余量」，不是抖动（2026-10-18 二次定位）

上面两条修完之后症状还在，**每个电台、每次都精确复现**，所以做了三份定量取证：

| # | 怎么测的 | 结论 |
|---|---|---|
| ① | 同一时刻并行抓「直连源站」和「走代理」的字节时序 | 两条曲线**逐字节一致**（30 秒各 295.3KB，抖动形态都一样）⇒ 代理是透明的，制造停顿的**不是**服务端 |
| ② | 每 200ms 采样设备 socket（`/proc/net/tcp6`）与 wlan0 累计 rx | 全程 ESTABLISHED、`rx_queue` **恒为 0**、收包速率稳定 ⇒ 服务端一直在给，设备也一直在读，**没有断流** |
| ③ | 同一时段抓 logcat | `NuPlayer: buffer low, pausing...` / `NuPlayerRenderer: now paused audio queue has 4 entries` / `NetPlayer4: HandleMediaInfoBufferingStart → PlayState 6`，**正好 3 秒后** `buffer ready, resuming...` ⇒ 是设备**自己按了暂停**（所以 Web 界面上图标会跳成暂停态） |

把三份证据合起来，真相是：

```
源站是 64kbps 实时流 ⇒ 供给速率（8KB/s）严格等于播放速率（8KB/s）
⇒ 设备没有天然余量，唯一的前瞻缓冲来自「连上瞬间源吐的那段开场爆量」
  （实测首 250ms 就爆 65KB ≈ 8 秒内容）
⇒ 这 8 秒播完，余量归零 ⇒ 任何抖动都会让 audio queue 见底
⇒ NuPlayer 暂停 3 秒攒一点 ⇒ 再播 ⇒ 循环。这就是 6 + 3。
```

对症的办法只有一条：**在点播那一刻给设备一大坨，让它一次吃饱**。
链路上能改的只有服务端这一侧，于是有了下面这套「常热」方案 —— 它**确实有效**，
但已经被**默认关掉**（理由见「5 号证」）：

| 改动 | 默认 | 作用 |
|---|---|---|
| **常热（pin）**：最后一个人走了也不关上游 | `RADIO_WARM=1` 才开 | 不用每次重连源 ⇒ ring 一直是热的 |
| **ring 放大** | `RADIO_RING` = 512KB（≈64 秒内容） | 「一次能给多少」的天花板，原来是 128KB |
| **启动预热**前 N 个电台 + 听过的台进 LRU | `RADIO_WARM_N` = 3 | 听众还没来，后台已经替他攒了几十秒 |
| **首吐前憋一会儿** | `RADIO_FIRST_MS` = 5000 | 冷启动也能多攒几十 KB；设备感受不到晚几秒出声，但能感受到不再卡 |

实测效果（本地起服务，预热 26 秒后点播同一电台）：

| | 冷启动 | 常热后 |
|---|---|---|
| 首 500ms 到手的字节 | ~65 KB（≈8 秒内容） | **239 KB（≈30 秒内容）** |
| 后续 45 秒 | 反复 buffer low（PlayState 6/7 交替） | **一次都没出现 buffering** |

### ★ 5 号证：常热有效但太贵，最终默认改回「直连」（2026-10-18 三次定位）

常热把 6+3 彻底消除了，但用户随即指出：**「没必要为了这 3 秒空档在服务器上
24h 不停缓冲电台，不值得」**，而且 `/api/radio/stat` 一度报 `warm: {n:51, max:8}`
（LRU 没生效 ⇒ **51 个台全部常热** ≈ 400KB/s ≈ **一天 34GB**）。

于是做了三次对照，逐格换变量：

| device 包 | 服务端 | 电台链路 | 结果 |
|---|---|---|---|
| 新（1.3.180，默认指 8100） | 8100 | 代理（**冷启动**） | **卡 6+3** |
| 旧（默认指 8010） | 8100 | 代理（**已热**，ring 满） | 不卡（采样 30.03s / 墙钟 30.03s，1:1 零停顿） |
| 旧 | 8010 | **直连源站** | 不卡（同样 1:1，零 buffering） |

250ms 脉冲检测（20 秒）给出的最后一块拼图：

| 链路 | 总吞吐 | 形态 |
|---|---|---|
| 8100 代理（有存量） | 20.57 KB/s | 首窗爆 1028 KB/s（一次倒 257KB），之后 5.5 / 10.9 交替 |
| 源站直连 | 10.73 KB/s | 前 0.75s 爆 65KB，之后 5.5 / 10.9 交替 |
| **两者稳态** | 都是 **≈8.2 KB/s** | 与 64kbps 播放消耗 8.0 KB/s **持平 ⇒ 零余量** |

结论：**卡不卡只取决于「点播那一瞬间给了多少」**，跟代理/直连本身无关；
而「服务器 24 小时替你攒」是唯一立竿见影、但代价最贵的办法。既然直连那条路
（8010 时代）用户本来就没抱怨过卡，**默认就回到直连，把常热整套关掉**：

| 开关 | 现在默认 | 说明 |
|---|---|---|
| `RADIO_PROXY` | **0** | 0 = `/index.json` 吐**原始 URL**，设备直连源站；`1` = 走 `/radio/<b64>` 代理 |
| `RADIO_WARM` | **0** | 0 = 不预热、不常热，没人听时**零条上游连接、零流量** |
| `RADIO_KEEPALIVE` | 300000 | 听完 5 分钟就彻底断开（旧值 2 小时） |

> 一个容易踩的坑：**「暂停不读上游」并不省带宽**。TCP 还连着，源站照写，
> 数据只是压在内核缓冲里，resume 时一样一股脑过来，平均速率仍是 8KB/s。
> 要真省流量只有**断开**一条路。

#### 全部电台相关环境变量（当前默认）

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `RADIO_PROXY` | **0** | ★ 0=直连源站（推荐），1=走本机 `/radio/<b64>` 代理 |
| `RADIO_WARM` | **0** | ★ 0=不预热不常热；1=开启常热（吃带宽，见上） |
| `RADIO_WARM_N` | 3 | 常热电台数量（`RADIO_WARM=1` 时才有意义） |
| `RADIO_WARM_IDLE` | 1800000 | 常热电台多久没人听就退温断开 |
| `RADIO_PREBUF` | 65536 | 起播预填充（64KB ≈ 8 秒内容） |
| `RADIO_FIRST_MS` | 5000 | ★ 首吐前至少憋这么久（攒多一点再给设备） |
| `RADIO_PREBUF_WAIT` | 3000 | 攒不够就开吐的兜底毫秒数（与上面取大者） |
| `RADIO_RING` | 524288 | ★ 上游 ring 上限，= 一次能给新订阅者多少（≈64 秒内容） |
| `RADIO_BUFFER` | 262144 | 单个客户端水库上限，超出丢最老的 |
| `RADIO_KEEPALIVE` | 300000 | 无人订阅后上游保留多久（5 分钟） |
| `RADIO_RETRY` | 10000 | 上游重连次数，近乎无限（很早 end 会被设备读成「播完」） |
| `RADIO_STALL` | 15000 | 多久没数据算上游卡死 |
| `RADIO_CONNECT` | 12000 | 连接 / 首字节超时 |

想确认「服务器有没有在偷偷缓冲电台」，直接看这个（默认应该是 `warm.off:true`、
`__total.bps = 0`，即没人听时一条上游都没有）：

```bash
curl -s http://<NAS>:8100/api/radio/stat | python -m json.tool
#   warm.off              true = 常热已关（默认）
#   warm.list[]           当前在保温的电台（关掉时应为空）
#   __total.bps/kbps      当前实时占用带宽；__total.mbPerDay = 按这个速率一天多少 MB
#   stats.<url>.ringLen   这台攒了多少字节（只对代理链路有意义）
#   stats.<url>.pin       true=常热
```

★ 顺手确认电台地址是不是直连：

### 电台听着还有问题时的现场诊断


### 本地中文歌显示成乱码（2026-10-19 修）

现象：`周杰伦 / 青花瓷` 这类老 MP3 在曲库里长成 `ÖÜ½ÜÂ× / Çà»¨´É`。

- **根因在服务端，不在音箱也不在 player**：老 MP3 的 ID3 标签正文其实是 GBK，
  但 frame 的 encoding 字节写的是 `0`（= ISO-8859-1）。music-metadata 照规范
  逐字节按 latin-1 解 ⇒ 出来一坨西欧重音字母。把字节取回、按 GBK 重解就对了。
- **为什么会复发**：2026-10-17 两个容器（`r1-music` 8010 Python + `mini-lx` 8100 Node）
  合并时，本地曲库用 Node 重写（`local.js`），把 Python 版 v1.4 里那段还原逻辑漏掉了。
- 修复放在 `local.js`：`toLatin1Bytes()` → `gbkPairs()` → `fixMojibake()`，
  再加 `looksBroken()` 让 `title='??'` 这种写坏的标签回退文件名。
- 误伤防线（比 Python 版更严，这两条是这次现场抓出来的）：
  | 判据 | 挡掉的误伤 |
  |---|---|
  | GBK 双字节的**尾字节只认 ≥ 0x80** | `Mötley Crüe`→`M鰐ley Cr黣`、`Jökulsárlón`（`ö+t`/`ü+e` 按 GBK 规范算合法双字节） |
  | 只有一对时必须在 GB2312 汉字区 | `öü`（F6FC，全高字节的一对）→ `鳇` |
- **缓存不会拖后腿**：`files/local_cache.json` 里已经存着乱码的那些条目，加载时就地
  修一遍（`v` 字段从缺到 2 触发），**不用重新扫 1000+ 首文件**，改完重启立刻生效。
- 自检：`curl http://<NAS>:8100/api/health` 的 `local` 段里有
  `gbk:true`（GBK 解码器可用）、`cacheV:2`、`mojibakeFixed:N`（本次修了几条缓存）。

## 5.5 本地有声书库（v1.2.0，独立目录）

和在线书库（落雪搜平台）并列的第二路来源：直接扫 NAS 上的**有声书专用目录**，
书名/集数从**文件名**里认，播放走 `/m/<rel>` 直链（内网 + Range，比在线取链快一个量级）。

```yaml
# docker-compose.yml
    volumes:
      - /volume1/audiobook:/audiobook      # ← 只放有声书的目录
    environment:
      - ABL_DIR=/audiobook                 # 想换目录就改这两处
```

**命名格式**（四种都认，2026-11-04 用户提供的真实样本）：

| 样本 | 解析结果 |
|---|---|
| `道诡异仙-第0集-引子.m4a` | 书=道诡异仙，集=0，标题=引子 |
| `凡人修仙传 第0集 预告.m4a` | 书=凡人修仙传，集=0，标题=预告（空格/全角空格都行） |
| `1.放开那个女巫-我就是四王子-ZmAudio.m4a` | 前置序号即集号；`-ZmAudio` 水印自动剥掉 |
| `三体139-【黑暗森林Ⅱ】第85集.mp3` | **合集**=三体（总集数=全部文件数），子书=黑暗森林Ⅱ，子书内第85集 |

- 合集（`【子书】`）：一层「三体 → 三本子书 → 各自的分集」，**每本子书各存一份播放记忆**，
  父级列表同时显示各部子书的记忆（`黑暗森林Ⅱ 第86集 · 死神永生Ⅲ 第1集`）。
- `001.mp3` 这种纯数字文件名也认：目录名当书名，数字当集号。
- 扫盘只读文件名（不读标签），几千个文件几毫秒；结果落盘 `files/ab_local.json`，
  容器重启秒开，之后后台再对齐盘上现状。加书/改名后在 Web 音源页点「重扫磁盘」即可。

接口（`?debug=1` 无关，全是只读/轻写）：

| 接口 | 用途 |
|---|---|
| `GET /api/abl/books?q=` | 书名列表（只给书名/集数/记忆，不吐集表） |
| `GET /api/abl/eps?id=&page=&size=&q=&ep=` | 某书/子书的集表；合集父级只回子书清单 |
| `POST/GET /api/abl/pos` | 记进度（按书/子书各一份，落 `files/ab_local_pos.json`） |
| `POST /api/abl/pos/clear` | 清记忆（合集=连子书一起清） |
| `GET /api/abl/rescan` | 强制重扫磁盘 |

开关：Web 音源页「本地有声书库」，落盘 `files/media_flags.json` 的 `abLocal`；
关掉后 `/api/abl/*` 一律当没有这本书（小智与 Web 都拿不到），`/m/` 也只在
「本地音乐库 或 本地有声书库」任一开着时放行。

### 5.5.1 书目录自带的元数据（v1.2.1）

有声书目录里常见这几个 sidecar（不是每本都有，有就用，没有就按文件名兜底）：

| 文件 | 取什么 | 用在哪 |
|---|---|---|
| `cover_small.jpg` / `cover.jpg` / `folder.jpg` | 封面 | 书列表缩略图（**优先 small**：6KB vs 287KB） |
| `reader.txt` | 演播（一行） | 书名下面那行「演播 传说中的方片K」 |
| `desc.txt` | 简介 | 详情页折叠展开（默认收起，R1 屏小） |
| `metadata.json` | `title` / `authors[]` / `narrators[]` / `publishedYear` / `description` / `chapters[]` | 干净的作者名、年份、总时长、**每集时长** |

`metadata.json` 是 Audiobookshelf 那套结构，`chapters[i]` 的 `start/end` 是**整本累计秒**：

```json
{"title":"道诡异仙","authors":["狐尾的笔\\传说中的方片k"],"narrators":["传说中的方片k"],
 "publishedYear":"2022","publisher":"ZmWeb","chapters":[{"id":0,"start":0,"end":157.86,"title":"…第0集-引子"}]}
```

- `end - start` = 这一集的时长。**只有 chapters 数与文件数相等时**才按顺序套用
  （对不上宁可不显示，也不把时长错配到别的集）——道诡异仙 1300↔1300、凡人修仙传 2114↔2114 实测吻合。
- `authors` 写法不统一（`狐尾的笔\传说中的方片k` / `忘语 / 光合积木`）⇒ 按 `\ / 、，;` 拆开再拼。
- 封面也走 `/m/<rel>`：`/m/` 现在**两个根都认**（音乐目录 + `ABL_DIR`），且图片给对 MIME
  （v1.2.0 只认音乐根，封面会 404；只给 audio/mpeg 浏览器也不显示）。
- **R1 侧自 pl-1.6.136 起固定不显示封面**（列表和弹窗都不显示）：设备 WebView 跨网拉 jpg
  基本拉不到，img 先把行高撑开再塌回去，看着像"加载失败变回纯列表"。所以 `cover` 字段照给
  （网页之外的客户端还能用），但 R1 网页不读它。
- **v1.2.2**：书列表里的 `cover` 改成**绝对地址**（`http://<NAS>:8100/m/…`）。相对地址会在
  R1 网页上打到设备 8080 去（页面是设备地址打开的），封面全 404——图裂但 `onerror` 一隐藏就看不出。
  集表的 `episodes[].url` 从 v1.2.0 起就是绝对地址，现在两边一致。
- **v1.2.3（2026-11-07）**：修「容器偶发意外停止」。`pipeAudio()` 原来用
  `signal: AbortSignal.timeout(20000)` 卡**整条流**——播放器一暂停/拖进度，下游不再读，
  `pipe` 的背压把上游 body 卡住没人消费，20 秒后 signal abort 让 body 流报错，
  而 `Readable.fromWeb(...)` 出来的流**没挂 error** ⇒ Node 报
  `Unhandled 'error' event` / `DOMException [TimeoutError]` 直接退出进程
  （compose 是 `restart: unless-stopped`，表现为「偶发停止」）。
  现在 20 秒只管「等到响应头」，拿到头立刻取消定时器；传输期换成 60 秒空闲看门狗
  （下游背压导致暂停不算上游死）；`src`/`res` 全挂 `error`，客户端断开就销毁上游流；
  另加进程级 `uncaughtException`/`unhandledRejection` 兜底。回归脚本见 `_tests/`。

顺带修的两个解析误伤（拿真实书库跑出来的）：

- `… 第088集 大婚【上】`：`【】` 以前一律当子书标记 ⇒ 一本书被劈成「上/下」两半（259 + 493）。
  现在要求**括号必须在集号之前**才算子书（三体 `【黑暗森林Ⅱ】第85集` 符合，庆余年不符合）。
- `道诡异仙-第53-追来的佛陀.m4a`（漏了「集」字）：以前另立一本单集书，还把整本章节数对不上、
  连累 1300 集全没时长。现在 `第N-` 也认。

R1 侧：`我的节目` 分两栏（在线 / 本地），本地栏点书名弹出三级（合集 → 子书 → 分集，
带返回按钮），播放时来源标签显示 **📖 本地节目**。

## 6. R1 侧收尾

- 音箱控制台（`:8080`）→ 音乐源只留 `http://<NAS>:8100/index.json`，删掉 8010 那行 → 保存。

  之后容器重建也是秒回。传了新歌就点 Web 上的 `/reindex`（或直接 `op=reload`）。

## 接口一览

| 路径 | 用途 |
|---|---|
| `/index.json` | **本地 + 在线 + 电台** 一次吐完（带 `onlineFrom` 标出在线段起点） |
| `/online.json` | 只吐在线池（R1「随机播放在线音乐」专用，关掉在线库时 `off:true`） |
| `/m/<path>` | 本地文件（支持 Range / 206） |
| `/radio/<b64url>` | **网络电台代理**（base64url 编码电台原始地址；预缓冲，抗公网抖动，详见上一节） |
| `/r/<source>/<rid>` | **在线曲目的播放地址**（惰性：起播那一刻才取链 + 转发） |
| `/s/<i>` | 池内第 i 首（同样惰性，保留兼容；列表里已不再用它） |
| `/r/ping` | 惰性地址探针（R1 用它决定要不要逐条取链） |
| `/api/lib` | **Web 曲库页的三块数据源**：`{local,online,radios}` 分开返回（各条带 `src`），前端不用再切分 |
| `/api/radios` | 网络电台清单读写：GET 拿列表，POST 用数组**整体覆盖** `files/radios.json` |
| `/api/search` | 在线搜歌（`?q=&source=all&limit=`）。每条都带 `url`（`/r/<源>/<rid>` 惰性地址），浏览器/音箱拿去就能播 |
| `/api/url` | 取链（只走落雪 docker） |
| `/api/lx` | 落雪 docker 地址的读写 |
| `/api/quality` | 默认音质读写：`GET` 看当前档，`POST {default:"128k"}` 改（128k/192k/320k） |
| `/api/media` | 三块开关的读写 |
| `/api/health` | 体检（含 `lx` / `media` / `localCount`） |
| `/reindex` | 重扫本地曲库 |

## 三块开关的口径

| 关掉哪块 | 会发生什么 |
|---|---|
| 本地音乐库 | `/index.json` 里本地曲目为 0，`/m/*` 一律 404，「随机播放」只剩在线 |
| 在线音乐库 | 在线段为空，`/online.json` 回 `off:true`，R1 自动改播本地曲库 |
| 网络电台 | `radios` 为空数组，语音点电台 = 没有 |
